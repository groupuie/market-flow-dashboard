## 6. 結果(出場重播)— 研究定義
- **進場**:鎖定時的買點(原快照、原尺度)固定;**不因後來的重新還原、四捨五入而重新選樣**(買點只在 §3 用原快照核對)
- **之後的 K 線**:v2 結案時存的 `bars_used`(訊號前一天起);第一根 = 下一個官方交易日、一天都不少、欄位合理、日期不重複
- **尺度**:`bars_used` 和快照重疊的兩根(訊號前一天、訊號日)全部 8 個價格(開高低收),在四捨五入半格(≥ 1 元 ±0.0005、< 1 元 ±0.000005)內要有**共同比例**;沒有 → 不可重現。有 → 歷史整段乘這個比例(**不再四捨五入**)接上 `bars_used`
- **出場**:凍結的賣法在接好的資料上重算;進場日、出場日、原因、報酬(差 < 1e-12)、進出場開盤價都要和帳上一樣,記錄時間不早於出場那根**官方收盤**(半日市 = 13:00 美東)→ 重現;否則不可重現(缺漏)
- 換尺度的風險(`rescale_risk_scan.py`):14,017 個真實買點(266 檔 + SPY / QQQ,2023-01 ~ 2026-07)× 5 種比例,假設進場後第 2 根除息 / 分割:出場對不上 1 / 0 / 3 / 1 / 1 筆(比例 0.999 / 0.995 / 0.98 / 0.5 / 0.25),約萬分之 0–2;重疊比例檢查誤擋 0 筆。對不上的都是「頂」的條件在第 3 位小數附近翻轉 → 依缺漏規則處理(不挑尺度)。粗估一個收案期幾百筆跨過配息,期望值不到 0.1 筆
- 限制:回答的是「固定訊號與固定規則在指定資料版本上的事件報酬」,不是「每天線上程式實際看到什麼」

## 7. 判定(只做一次)
- **時間**:收案期最後一天之後 ≥ 41 個交易日,而且每一筆都有結果或已分到缺漏(41 + 10 天還沒結果 → 缺漏)
- **結案截止**(草案 4 寫清楚):收案期最後一天之後**第 51 個交易日的官方收盤**(manifest 的 `resolve_by`)之前沒有結果紀錄的,一律算缺漏 — **之後才補的結果也算缺漏**。這樣判定和「哪一天按下正式判定」無關(不能等一等、讓晚到的結果進來)。結果紀錄的時間以收集程式寫的 `closed_utc` 為準(限制見 §13);晚於分析時點的紀錄當作那時還沒有
- **門檻(沒過 = 資訊不足)**:已結束 ≥ 300、同意 ≥ 60、不同意 ≥ 60、配對日期 ≥ 80、兩邊各 ≥ 30 家發行人、批次覆蓋 ≥ 90%、沒有缺漏的不同意、有效重抽 ≥ 90%
- **缺漏**:缺的同意 = −100%(目前的乘法成本與非負股價下,這是真下界);缺的不同意沒有有限上界 → 資訊不足;q05 / q95 只當壓力情境;另報翻轉點
- **H1**:§2 的區間下界 > 0;排除缺漏、缺的同意 = −100% 兩種都要成立
- **H2(使用者凍結時三選一)**:甲 同意勝率 − 全部勝率 ≥ 10 點 / 乙 事件加權的同意 − 不同意勝率差下界 > 0 / 丙 不要 H2(勝率只描述);程式一次算三種,正式只用 manifest 寫的那一種,**不能三種都看完再挑**
- **PASS** = 門檻 + H1 + H2;**上線候選** = PASS 且 H3(同意組本身扣成本平均的下界 > 0,兩種缺漏算法)— 之後還要用固定判讀重播「一次一筆、只亮同意」的持倉路徑 + 使用者同意,才可能上線
- **唯一一次 = 一個實驗只有一份結果**(草案 4 改;Astra v0.7.5 §3.3):不是靠「本機檔不存在才建立」,而是**先公開登記這次要用的輸入,再算;之後重跑只會照登記重播:同一個計算環境得到同一份位元組,不同就停**(§8)。草案 3 的缺口:結果寫在本機、還沒 commit 前被刪,就能再跑一次;另一個 checkout 也沒有共用的防重紀錄 — 現在兩種情況都只會重播同一份結果(或停),不會有第二個可挑的答案

## 8. 正式模式(草案 4;凍結前用構造的成熟批次驗收過,§11)
1. **先抓遠端**(main 與 astra-ledger);之後全部以遠端為準(本機自己的分支不能當輸入)
2. 讀 git(main)裡的 `research/ledger_v3/v3_manifest.json`;工作區有就要一模一樣;**只被一個 commit 寫過**(= 凍結 commit)
3. **自我指紋**:正在執行的程式 = manifest 記的 SHA-256 = git 裡 main 和凍結 commit 的那一份;凍結之後沒被改
4. **固定規格**:程式裡除了使用者決定的兩項(收案長度、H2)以外全部 = manifest;兩項只能是允許的選項
5. **官方日曆**指紋(含逐日開收盤)、收案日曆指紋、結案截止日 = manifest
6. **實驗 ID**、判定檔、錨點、開跑登記的固定位置 = 由 manifest 內容算出的
7. **凍結錨點**:astra-ledger 上 `v3_freeze/<實驗 ID>.json`(manifest 指紋 + 凍結 commit),只被一個 commit 寫過;它的 ledger-receipt run 時間 **早於起日官方收盤**
8. **開跑登記**(astra-ledger 上 `v3_freeze/<實驗 ID>.start.json`):
   - 還沒有 → 先確認 READY(只看筆數,不算結果;不是 READY → 停,什麼都不寫)→ 寫登記:實驗 ID、manifest 指紋、凍結 commit、程式指紋、**ledger 輸入 commit(= 當下遠端 astra-ledger 最新)、main 輸入 commit**、本機時間、計算環境(Python 主次版本 + NumPy 版本)、證據修復紀錄 → 在 ledger 輸入上**只加這一個檔**、push(只能快轉)→ 從遠端讀回核對 → 等到 GitHub 的 ledger-receipt 收件(第三方時間)。push 被拒 → 停(什麼都沒算,直接重跑);收不到收件 → 停(之後重跑會讀到登記、照登記重播)
   - 已經有 → 核對:只被一個 commit 碰過、內容是程式寫的標準格式、manifest / 凍結 commit / 程式指紋對、那個 commit 的上一個 commit = 登記的 ledger 輸入而且只加這個檔、main 輸入在遠端 main 上、計算環境一樣、有 GitHub 收件;任何一項不對 → 停
9. **計算**:只用登記的 ledger / main commit,時間 = 登記的 GitHub 收件時間 → 同一份登記,在**同一個計算環境**(同版 NumPy、同 Python 主次版本)重跑都得到同一份位元組(之後 ledger 又有新 commit 也不影響)。作業系統的數學函式庫沒有固定:換一台電腦若位元組不同,保存時比對不符 → 停(不會出現第二個答案,但要查原因)
10. **保存**:判定檔(含登記、錨點、狀態、結果)commit + push 到遠端 main → 從遠端讀回、逐位元組核對 → 才叫「已保存」(PERSISTED)。push 一直失敗 → 停,狀態 = **未持久完成**;重跑會照同一份登記重播、得到同一份結果、再存一次。遠端已經有一模一樣的 → 回報「已保存、重播相同」,不寫任何東西;遠端有但不一樣(或被改過)→ 停
11. 時間只從系統時鐘來;命令列不能給「今天」、規格、離線、輸出位置、分支
- **這個設計回答的是**:「同一個實驗會不會因為重跑、刪檔、換 checkout 而得到第二個可以挑的正式答案?」→ 不會:同環境重播得到同一份;不同就停。**沒有回答的**:
  - 誰都可以拿公開的帳本自己私下先算(帳本本來就是公開的)
  - 「登記的時間」還有一個影響管道:登記用的 main 輸入 = 當下的遠端 main。若在 READY 之後、登記之前有人改了三支凍結引擎,`engine_changes_on_main` 會讓所有批次不合格 → 資訊不足。這只能把結果變成「沒有結論」、不能變成 PASS,而且改動留在 git 歷史;要不要把這條檢查改成「以收案期結束時的 main 為準」,請 Astra 決定(本輪沒改)。其他時間差由結案截止(§7)消除
  - 登記之後 GitHub 一直沒有建 ledger-receipt run(Actions 被關、事件遺失):程式會一直停,實驗卡住(不會出現第二個答案);**復原規則還沒寫**,候選:登記後超過一段固定時間仍無收件,才允許一份輸入完全相同的補登記
  - 前提:遠端分支不能被強制改寫歷史(建議在 GitHub 打開 main / astra-ledger 的分支保護;使用者在網頁設定,選做)

### 12.1 28.3% 是什麼、不是什麼
- 歷史庫(265 檔 × 2,659 個交易日,2016-01-04 ~ 2026-07-31)逐格算:43.3% 的「股票 × 日」有持有中的事件;**假設每筆判讀獨立、同意機率固定 43%** 時,至少一筆持有中的「不同意」占 **28.3%**(Astra 獨立重算一致:43.31448% / 28.29139%)
- 這是**從歷史股票日均勻抽一格**的占比,**不是「發生下市時」的條件機率**:下市 / 收購的標的與時點可能和持倉、跌幅、判讀、資料缺口有關(同一個 28.3% 的無條件占比,條件機率可以是 0%,也可以是 100%)
- 草案 3 寫的「遇 3 次 → 約 63% 白做」還多假設三次互相獨立(完全相關 = 28.3%、互斥可到 84.9%)→ 只是情境計算,**不是**已被資料證明的試驗失效機率
- 改成的說法:「嚴格缺漏規則可能讓試驗資訊不足;在均勻股票日、每筆獨立且同意機率 43% 的假設下,占比約 28.3%。實際發生的風險還沒有估計。」

### 12.2 「最後收盤價」不是不同意組的保守上界(草案 3 的候選乙撤回)
- H1 = 同意 − 不同意。缺的不同意若補得**比真實低**,H1 會被**高估**(往有利 AI 的方向)
- 構造例(數學反例,不是某檔股票的歷史):進場 100、最後看得到的收盤 100、最後依約收到現金 120;每邊成本 0.1%、同意組 +10% → 用最後收盤補:不同意 −0.1998%、H1 = **+10.1998 點**;用最終給付:不同意 +19.7602%、H1 = **−9.7602 點**。只缺不同意時,「缺的同意 = −100%」不會發動,補救不了這個偏差
- 收購對價可能是現金、股票或混合;下市後也可能在場外繼續交易;資料商不再提供舊代號 ≠ 股東最終拿到多少。帳本每天的 `unreal` 只證明「當時記過這個值」,不證明之後還能用這個價賣、也不是最終給付的上界;事後才指定「在最後那根收盤賣掉」也不是當時能執行的交易規則
- 所以「末價填補」不能稱為保守界;若要用,必須承認估計對象改了(變成「依指定缺漏估值規則得到的報酬」),另外預先登記

### 12.3 終值與缺漏規格(草案;本輪**不採用**新政策、**不新增排程**,先把規格寫清楚給 Astra 看,之後給使用者選)
處理順序(照 Astra v0.7.5 §4.3):
1. **先分類、保存官方來源**:結案截止(§7)前沒有結果的每一筆,先查原因並分成 — 資料商故障(照常交易、只是抓不到)/ 代號變更 / 現金收購 / 換股(含現金 + 股票)/ 停牌 / 破產或強制下市 / 查不到原因。每一類都要保存**官方事件來源與生效日**(SEC EDGAR 申報的 accession number 與檔案 SHA-256、交易所 Form 25 下市通知、公司公告)與查詢時間,commit 進 git 並拿到 GitHub 收件,而且要在**開跑登記之前**
2. **能重建的才重建,規則事先寫死**:
   - 資料商故障 / 代號變更:用事先指定的第二資料源(或新代號)補 K 線,照凍結賣法重播;有效來源與查到哪天為止,事先寫定
   - 現金收購:出場值 = 官方文件的每股現金對價;前提是能證明**到最後交易日為止凍結賣法都沒有觸發**(要有到那天為止的完整 K 線;觸發過就照賣法結果,不用終值)
   - 換股 / 混合:出場值 = 現金部分 + 換股比例 × 收購方在「目標最後交易日的下一個交易日」的官方開盤價(估值時點事先寫死;有選擇權或比例分配時用公告的預設對價或最終結果)
   - 成本照正式口徑(乘法 × 0.999 ÷ 1.001)
3. **重建不了、而且不同意那邊沒有可信上界 → 維持「資訊不足」**;只另外報事先寫好的敏感度 / 翻轉點(§7 已有),不拿最後收盤當最壞界
4. **每日 K 線封存**(草案 3 的候選丙)有助於第 2 點的「到最後交易日為止賣法沒觸發」與發現缺日,但**補不出收購對價或下市後終值**;若要新增封存工作,要和終值規則一起設計,並經使用者同意新增排程
- **驗收測試要先寫好**(構造例、不連網):現金收購 120 → 不同意 +19.7602%;換股 → 依寫死的估值時點;最後交易日前賣法已觸發 → 照賣法、不用終值;查不到原因 → 資訊不足;官方來源晚於開跑登記 → 不收
- **使用者凍結時的選項**:甲 維持嚴格(現行;最簡單,可能較常資訊不足)/ 乙′ 嚴格 + 第 1–3 點的終值重建(每一件下市要人工查證;要有到最後交易日為止的 K 線 — 現有帳本不一定有)/ 丙′ 乙′ + 只新增的每日封存(新增排程,要使用者同意)。三種都**不用**末價填補

## 13. 已知限制
- C1 在一般資料偏保守(標準誤約實際 1.3–1.5 倍)→ 功效有代價;在單筆格子很多、極端值很多的結構,誤判率大約在名目附近(1.5–3.0%)
- 換尺度重播:極少數(約萬分之 0–2)跨過配息 / 分割的筆會因第 3 位小數不同而對不上 → 算缺漏;若剛好是不同意 → 資訊不足
- 零訊號日與鎖定日的「候選清單完整」都由凍結引擎當時的執行保證(收集程式沒存每一檔的 K 線)
- 提示詞要模型判「會賺的機會比平常高」,H1 比平均報酬差:兩者不同;v3 不改提示詞
- 排程提示詞 = `prompt_v2.md`(SHA-256 `1bfc25e3…`)只有帳號擁有者看得到;模型 ID 是判讀檔自報
- 遠端回條證明「GitHub 至遲已持有這個 commit」,不是推論當下的證明
- 事件研究,不是一到兩檔的帳戶績效;P1 / P2 的指標回看期不在日期序列檢查範圍
- P1 / P2 的 s3 只驗 manifest 與 SPY 的位元組,`PB.load()` 不逐檔重算其他股票檔的雜湊:重用同一份經 s2 核實的不可變快照時成立;換地方或換時間重跑,要先重驗全部原始檔指紋。s3 的共同日曆是那份 SPY 行情的日期,不是重新核對過的官方交易所日曆;個股日期異常是記錄下來,不是一發現就停
- 結案截止用收集程式自己寫的 `closed_utc` 判斷;更嚴的做法是用「第一次出現這筆結果的 score commit 的 GitHub 收件時間」(之後可加,這輪沒做)
- 開跑登記 / 判定檔的防重,前提是遠端歷史不會被強制改寫;建議在 GitHub 打開 main 與 astra-ledger 的分支保護(使用者在網頁設定,選做)
- 決定性重播要同一版 NumPy(亂數演算法跨版本不保證相同)與同一個 Python 主次版本;換了 → 停,要裝回登記的版本再跑。作業系統的數學函式庫(`math.lgamma` 等)沒有固定;「另一個 checkout 相同」的測試是在同一台機器上做的
- 登記時間仍能透過 main 輸入影響結果:READY 之後、登記之前若有人改了凍結引擎 → 所有批次不合格(只會變成資訊不足,不會變成 PASS)
- 登記之後若 GitHub 一直沒建收件 run → 實驗卡住;補登記的規則還沒寫
- 正式判定會 push 兩個新檔:astra-ledger 上的開跑登記、main 上的判定檔(只新增;收集程式遇到 push 衝突本來就會 fetch + rebase 重試)
- 時段表只到 2028-12-29;更晚的起日(含 250 天收案 + 51 天結案)在 make-manifest 就會停
