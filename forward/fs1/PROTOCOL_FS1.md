# FS1 預先登記:Claude 每月板塊判斷的往前封存(美國 49 產業)

- 版本:v1.0|2026-10-23 21:06:11(台灣)|簡述:往前封存
- 起因:使用者 2026-10-23 的決定 ——「要,設每月排程」(每月封存 Claude 的板塊判斷,排全部 49 個細產業,同時封存簡單動能的排序當對照);Codex「主線改回中期盤感」v1.0 與 R8 v1.0 的前瞻卡要求(資訊 → 不同判斷 → 排序 / 配置 → 失效條件 → 評分);Claude v5.0、v5.1。
- 這份協定與 `scripts/` 在**第一張卡封存之前**推上 `sector-forward-ledger` 分支(GitHub 伺服器端的 push 紀錄 = 時間證據)。程式只用假資料測過(`scripts/fs_selftest.py`)。
- 不下單、不是投資建議。

## 1. 問題

Claude 用公開資訊與自己的知識,每月月底替 49 個產業排「未來 3 個月誰比較強」,有沒有比**同一時間、同一份資料**算出的簡單產業動能(S0_fwd)更準?(另看 1、6 個月。)

## 2. 名單與資料

- 評分名單:Ken French 資料庫的 49 產業**市值加權**月報酬(含股息;`industries49.json` 是代號、英文名、中文名,順序 = French 欄位順序)。市場 = F-F 的 Mkt-RF + RF。
- 每次執行時從 French 網站下載最新檔;資料包存檔頭的 CRSP 版本、SHA-256、最近 13 個月的報酬(S0_fwd 可以只用資料包重算)。

## 3. 時間

- 決定月 t:每個月一次;**第一個 t = 2026-10**(2026-11-01 執行)。
- 排程:每月 1 日 08:41(台灣)= 美東前一天晚上,月 t 最後一個交易日收盤之後、月 t+1 開盤之前;同一天 20:41(台灣,= 美東當天早上開盤前)再跑一次備援 —— 第一次已封存就只印「已完成」並評分,第一次失敗才會補做。
- 截止時間 cutoff_utc = `fs_prep.py` 執行的時間;資料卡引用的來源發布日期都不能晚於它。
- 封存期限 = 月 t+1 第一個平日 09:30(美東;假日不另外處理,偏保守)。超過期限才封存 → `late = true`,**不進主要分析**;超過期限之後 `fs_prep.py` 拒絕再做這個月。
- 漏掉的月份:期限前可以手動重跑;過了就記為缺,不補。缺與遲到的月數照實報告。

## 4. 對照組 S0_fwd(和卡片同時封存)

- m = min(French 最新月份, t−1);每個產業 = 月 m−10 ~ m 共 11 個月的累計報酬;同分照欄位順序;排出 1 ~ 49 名。
- m = t−1 時就是 SR1 的 S0(12−1 動能);French 多晚一個月時是 R7 式的 j−13 ~ j−3。資料包記 m 與落後月數。

## 5. 資料卡格式 `fs1-card-v1`(`scripts/fs_validate.py` 逐項檢查)

| 欄位 | 規則 |
|---|---|
| schema | `"fs1-card-v1"` |
| decision_month、cutoff_utc、packet_sha256、prev_card_sha256 | 照抄 `fs_prep.py` 的輸出(雜湊鏈:每張卡記上一張卡的 SHA-256;第一張是 null) |
| model | 判斷者的模型 ID |
| regime_view | 景氣與資金面一段話 |
| ranking | 49 個代號全部排序,最看好在前,每個剛好一次 |
| exp_excess_3m_pct | 每個產業預期未來 3 個月報酬減大盤(百分點);照 ranking 由大到小(可以相等) |
| weights | 只做多;鍵 = 產業代號或 CASH;每個 ≥ 0、單一產業 ≤ 0.15;加總 = 1 |
| calls | over 3 ~ 10 個(必須在前 10 名)、under 0 ~ 5 個(必須在後 10 名);每個要有 industry、side、p_beat_market_3m(0 ~ 1)、horizon_months(1 ~ 6 的整數)、thesis、differs_from_consensus、marginal_buyer、catalysts、falsifiers(≥ 1)、add_if、exit_if(≥ 1)、claim_ids(≥ 1,要指到 claims) |
| claims | ≥ 5 條;每條 id(不重複)、text、source_url(http/https)、published(YYYY-MM-DD 或 ISO,不晚於截止)、consensus(不知道寫 unknown) |
| notes | 49 個產業每個一句(1 ~ 60 字) |
| changes_vs_prev | 有上一張卡時必填(改了什麼、上一張卡的加碼 / 退出條件有沒有觸發);第一張卡 null |
| searches_used | 0 ~ 15 的整數 |

不能有其他欄位。檢查只管格式與欄位關係,不核實來源內容;檢查沒過只能修格式,不能改判斷。

## 6. 每月流程(排程,提示原文在 `schedule_prompt.txt`)

1. `fs_prep.py`:決定月、截止時間、下載 French、算 S0_fwd、寫資料包 `pending/{t}.packet.json`;已封存的月份印「已完成」。
2. Claude 讀資料包、§5、上一張卡、`scores/summary.md`;最多 15 次網路搜尋;寫資料卡 `pending/{t}.card.json`。
3. `fs_validate.py` → `fs_seal.py`:卡片與資料包原樣存進 `cards/{t}.json`、`packets/{t}.json`,`ledger.jsonl` 追加一列(兩個 SHA-256、上一張卡的 SHA-256、截止與封存時間、late、模型),commit 並推上 `sector-forward-ledger`。已封存的月份不能再封存或改寫。
4. `fs_score.py`:French 資料涵蓋 t+1 ~ t+h 之後,算 h = 1、3、6 的結果,追加到 `scores/scores.jsonl`(只追加;卡片或資料包的指紋和 ledger 不同就不評分並回報),重寫 `scores/summary.md`。

## 7. 評分(全部事先固定)

- R_i(t, h) = 月 t+1 ~ t+h 的累計報酬(French 49 產業);缺任何一個月的產業不算。
- IC_C(t, h) = Claude 的排序與 R(t, h) 的 Spearman 相關;IC_S0(t, h) 同樣用 S0_fwd 的排序;差 D_h(t) = IC_C − IC_S0。
- **主要**:D3 的平均 ≠ 0。用 2026-10 ~ 2029-09 共 36 個決定月裡**準時且通過檢查**的卡;Newey–West 標準誤(Bartlett,落後 2),t 分布、雙尾 5%。只在 French 資料涵蓋到 2029-12 之後算**一次**,寫入 `scores/final_primary.json`,之後不覆寫。中間的摘要都是描述性的;不提早停止、不改規則。
- **次要**(Holm,4 個):D1(落後 1)、D6(落後 5)、前 10 名等權 3 個月報酬 Claude − S0(落後 2)、權重組合下 1 個月報酬 − 市場(落後 1)。
- **只報告**:IC 本身、calls 的 Brier(3 個月是否贏市場)、遲到與缺的月數、不同模型分開的結果。
- 評分用第一個涵蓋所需月份的 French 檔;之後的修訂版只當敏感度。

## 8. 功效(先講清楚)

虛無假設下 49 產業每月 IC 的標準差約 1/√48 ≈ 0.14。若 Claude 的真實 IC 是 0.05(和簡單動能差不多),檢定「IC > 0」3 年的功效約 55%、10 年約 97%;檢定「比 S0 好」的差距更小,功效更低。36 個月只看得出很大的差距;結果不顯著不代表沒有,顯著也要看是不是集中在少數月份。2029-09 之後照同樣方法繼續描述。

## 9. 已知限制

- 往前封存沒有「知道答案」的問題,但判斷者知道產業動能的歷史證據;這是允許的(要測的是 Claude 有沒有加分)。
- 來源網頁之後可能被改或消失;卡片只存網址、發布日期與一句話。
- 排程用平台預設的模型,模型可能隨時間改變;每張卡記模型 ID,結果分開報告。
- French 產業組合不是可交易的 ETF,而且資料會回溯修訂;沒有交易成本。
- GitHub commit 的作者 / 提交時間不足以獨立證明;以伺服器端的 push 紀錄當時間證據、SHA-256 當內容證據。「先封存、後有答案」是唯一的保證。

## 10. 變更規則

- 協定與程式在這次 commit 凍結。程式錯誤可以更正(另記版本與原因),**不能改已封存的卡、資料包或已寫入的評分列**。
- 要更正一張卡的內容,只能在之後的卡的 changes_vs_prev 說明;主要分析永遠用原本封存的版本。
